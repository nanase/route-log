# クラウド API と同期

API は走行単位の REST とし、同期は「走行全体を送る」単純な方式から始めます。利用者は本人 1 人の想定で、競合解決は `updated_at` による楽観ロックで足ります。

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | /api/rides | 走行の一覧（id, title, ride_date, updated_at） |
| GET | /api/rides/:id | 走行の全データ（ride, waypoints, events, 経路） |
| PUT | /api/rides/:id | 走行の全データを置き換え。`If-Match: <updated_at>` で競合を検出 |
| DELETE | /api/rides/:id | 走行の削除（R2 の経路も削除） |
| GET | /api/public/rides/:id | 公開走行の閲覧用データ（is_public = 1 のみ、後回し） |

## 認証

- `/api/*`（public 以外）は Cloudflare Access で保護する
- Tauri アプリはサービストークン（`CF-Access-Client-Id` / `CF-Access-Client-Secret`）をヘッダーに付けて呼ぶ
- トークンは OS の資格情報ストア（Windows 資格情報マネージャー、`keyring` crate）に保存する
- `/api/public/*` は Access の対象外にし、Worker 側で is_public を確認する
- Worker 側でも `Cf-Access-Jwt-Assertion` の署名・`iss`・`aud`・期限を検証する
  - Access のポリシーが外れたときに、書き込みの経路へ要求が素通りしないためである
  - 設定が欠けているときは、すべての要求を拒む
- 検証は `routelog-access` crate が持つ。入出力を持たない純粋な Rust で、RS256 の署名・`iss`・`aud`・期限を確かめる
  - 人のログインは `email`、サービストークンは `common_name`（クライアント ID）を持ち主として読む
  - 拒んだ理由は外へ出さず、どれも同じ 403 で返す
- Access の公開鍵は Worker が取りに行き、1 時間使い回す

## Worker の実装

- `workers-rs` で実装し、D1 と R2 をバインドする
- PUT は D1 のバッチ（トランザクション）で ride 配下を置き換え、経路 GeoJSON を R2 に保存する
  - 経由地とイベントは、変わった行だけを書く。送られてきた中に無い行を消し、ある行は中身が違うときだけ書き換える
  - イベントは中身を見ずに、送られてきた JSON のまま持つ。確かめるのは、列に出す値（ID・種類・名前・位置・状態）があることだけ
    - 当初はイベントを型に読んでいた。アプリにイベントの種類を足すと、Worker を入れ替えるまで、その走行を 400 で拒んだ
    - 以前の形のイベントをいまの形に直すのは、アプリが読むときに行う
  - 読めない走行を拒むときは、読めない理由を本文に入れる。アプリは、それを「未同期」の理由に出す
  - 書いた行数を、応答の `rows_written` で返す。理由と測った値は [D1 の書き込みの行数](#d1-の書き込みの行数) にある
- インフラ設定は `wrangler.toml` で管理する
  - `account_id` は書かない。手元は `wrangler login`、Actions は environment のシークレットから渡す
  - `workers_dev = false` にし、`[[routes]]` の `custom_domain = true` でホスト名を決める
  - Access のチームのドメインは `[vars]`、`aud` はシークレットに置く
  - マイグレーションは連番の SQL と戻し用の SQL を持ち、デプロイの前に適用する（[設定とデプロイ](../guides/deployment.md#マイグレーション)）
- イベントは、絞り込みに使う値（kind・label・route_m・time_ms・status）を列に出し、全体を `json` の列に持つ。項目が増えても列を足さずに往復できる
- 経路の線は、区間ごとの頂点（`route.segments`）を JSON にして R2 の `rides/<ID>/route.json` に置く
- PUT は、すでにある走行について `If-Match` がサーバの持つ更新時刻と同じときだけ置き換える。違えば 412 と、いまの更新時刻を返す
- リリースのプロファイルに `strip` は付けない。付けると wasm-bindgen が要る情報まで消え、ビルドが止まる
- Worker は wasm 向けなので、Cargo workspace の `default-members` から外す。ふだんの `cargo test` や `cargo clippy` の対象にならない

## アプリからの同期

同期は自動で行います。人が押して送り受けする操作は無く、上の帯に保存と同期の状態を 1 つ出します。走行は丸ごと送り、丸ごと受け取ります。

| きっかけ | すること |
| --- | --- |
| 走行を保存した | 3 秒待って、その走行を送る。待つ間に次の保存が来たら、待ち直す |
| 起動した | 手元とクラウドを突き合わせ、下の表のとおりに送り受けする |
| 接続先を保存した、走行の切り替えの板を開いた | 同じく突き合わせる |
| 同期できなかった | 60 秒待って、突き合わせ直す |

突き合わせでは、走行ごとに手元とクラウドの関係を決め、することを決めます。

| 関係 | 見分け方 | すること |
| --- | --- | --- |
| 同じ | 手元とクラウドの更新時刻が同じ | なし |
| 手元が新しい | クラウドの更新時刻が、最後に同期したときのまま | 送る |
| クラウドが新しい | 手元の更新時刻が、最後に同期したときのまま | 受け取る |
| 手元だけ | 手元にしか無い | 送る |
| クラウドだけ | クラウドにしか無い | 受け取る |
| 両方で変更 | どちらも、最後に同期したときと違う | 人に聞く。勝手には上書きしない |

- 最後に同期したときの更新時刻は、走行ごとにデータフォルダの `sync.json` に覚える
- 更新時刻はミリ秒まで持つ。秒までだと、同期の直後に直した走行が「同じ」に見える
- 突き合わせで「同じ」と分かった走行は、覚えも合わせ直す。送ったあとの応答を受け取れなかったときに、覚えだけが古く残るためである
- 起動のときの突き合わせは裏で行い、画面を出すのを待たせない
- 一覧を取ったあとで保存・送信・削除などがあった走行は、その一覧のとおりにはせず、もう一度突き合わせる

## 上の帯の表示

| 表示 | 意味 |
| --- | --- |
| 保存中… | 手元に書いている。続けて編集していて、保存を待っている間もこれを出す |
| 同期中… | クラウドへ送っている。受け取っている間と、送るのを待っている 3 秒の間もこれを出す |
| 同期済み | 手元とクラウドが同じ |
| 未同期 | 同期できなかった。次の保存か、60 秒後にもう一度試す |
| 両方で変更 | どちらを残すかを聞いている。押すと、走行の切り替えの板が開く |
| 保存済み | 同期を設定していないときに、同期済みの代わりに出す |
| 保存できません | 手元に保存できなかった。やり直すボタンを添える |

- 開いている走行だけでなく、すべての走行をまとめて 1 つ出す。開いていない走行が両方で変わったときも、気づけるようにするためである
- 先に見るものから順に、保存、同期中、両方で変更、未同期、同期済みである
- 同期を設定していないのは、API の URL かサービストークンが無いときである
- 走行ごとの状態は、走行の切り替えの板に小さく出す

## 送る

- 続けて編集している間は送らない。保存が 3 秒より短い間隔で続く間は、待ち直しが続く
- 同じ走行の送り受けは 1 つずつ行い、重ねない。送っている間に次の保存が来たら、済んでから最新を送る
- PUT には、最後に同期したときの更新時刻を `If-Match` で付ける。412 が返ったら送らず、「両方で変更」にする
- 推定した時刻は送らない。時刻を 1 つ確定すると、まわりのイベントの推定がみな動く。推定まで送ると、確定のたびに多くの行を書き換えさせることになる

## 受け取る

- クラウドから取ってくるのと、手元に置くのを分ける。取ってくる間は、編集も保存も待たせない
- クラウドには推定した時刻が無いので、取ってきたら、経路と確定した時刻から求め直す
- 手元に置くのは、編集の列に並べて行う。編集の途中に挟まると、画面に残った古い内容で上書きしてしまう
  - 保存の予約も、この列の中でだけ立てる。抽出のし直しと、保存のやり直しも列に並べる
- 手元の走行の更新時刻が、突き合わせたときのままであることを確かめてから置く。違えば置かず、「両方で変更」にする
- 開いている走行なら、保存を待っている編集を先に保存する。保存で手元が変わるので、上の決まりで置かないことになり、編集は残る
- 開いている走行を置いたら、画面を読み直して、右下に知らせる。取り消せる編集は無くなる
- 起動が済んでも何も開いていなければ、受け取った走行を開く

## 同期できないとき

- 編集と保存は止めない
- 上の帯を「未同期」にし、右下に知らせを 1 度だけ出す。赤い帯は出さない。理由は、「未同期」にマウスを重ねると読める
- 60 秒ごとに突き合わせ直す。アプリが動いている間だけ繰り返す
- 次の保存で送れたら、残りも待たずに突き合わせ直す
- 繋ぐまでの待ち時間は 10 秒、1 回の通信は 30 秒で切る

## 両方で変わったとき

- どちらでも上書きしない。上の帯を「両方で変更」にし、上の帯の下に知らせを 1 度出す
- 走行の切り替えの板で、「手元で上書き」か「クラウドで上書き」を選ぶ
- 選ぶまで、その走行は保存しても送らない。手元への保存は続く
- 選んだときに通信できなければ、「両方で変更」のまま残る

## 消す

- 走行の記録を消すと、クラウドからも消える。手元だけを消すと、次の起動で受け取り直して戻ってしまう
- クラウドから先に消す。消せなければ手元の記録も消さず、理由を板に出す。通信できるときに、もう一度消す
- 送り受けの最中の走行は、済むのを待ってから消す。受け取っている途中なら、取ってきた内容は手元に置かない
- 1 度も同期していない走行はクラウドに無いので、通信できなくても消せる
- クラウドにだけあって、まだ受け取れていない走行も、板から消せる
- 消した走行の、最後に同期したときの更新時刻は `sync.json` からも消す
- 別の端末の手元に残っている走行は、その端末を起動すると「手元だけ」として送り直され、クラウドに戻る。防ぐには、その端末でも消す
  - クラウドに無い走行を自動で手元から消すことはしない。接続先を替えたときや、クラウドの側を作り直したときに、手元の走行をすべて失うためである

## 作りの分担

| 置き場所 | 受け持つこと | 確かめ方 |
| --- | --- | --- |
| `app/src/lib/sync.ts` | いつ送り、いつ受け取り、失敗したらどうするか。上の帯に出す状態の決め方 | `bun test`。通信と画面を差し替えて試す |
| `app/src-tauri/src/sync.rs` の `classify`・`reconcile` | 走行ごとの関係と、することを決める。通信もファイルの読み書きもしない | `cargo test` |
| `app/src-tauri/src/sync.rs` のコマンド | 走行 1 つ分の送り受け | [同期の確認](../guides/development.md#同期の確認) |
| `app/src/App.svelte` | 保存のたびに知らせる。受け取った走行を、編集の列に並べて置く | 同上 |

| コマンド | すること |
| --- | --- |
| `sync_list` | 手元とクラウドを突き合わせた一覧を返す。走行ごとに、関係とすることが付く |
| `sync_push` | 手元の走行を送る。クラウドが書き換えられていたら、送らずにそのことを返す。上書きの指定があれば、それでも置き換える |
| `sync_fetch` | クラウドの走行を取ってくる。手元には置かない |
| `sync_apply` | 取ってきた走行を手元に置く。手元の更新時刻が違えば置かない。上書きの指定があれば、確かめずに置く |
| `sync_delete` | クラウドの走行を消す |

## 接続先

- API の URL とサービストークンは、設定のダイアログの「クラウド同期の接続先」で入れる。保存すると、すぐ突き合わせる
- API の URL は `config.json` に、サービストークンは OS の資格情報ストアに置く
- 通信は `ureq` で行う。アプリが送り受けするのは走行の JSON だけなので、非同期のクライアントは要らない
- 環境変数 `ROUTELOG_SYNC_JWT` があれば、サービストークンの代わりにそのトークンを送る。手元で動かした Worker に繋いで確かめるためのもので、Access を通す本番では意味を持たない

Cloudflare 側の作り方は [設定とデプロイ](../guides/deployment.md) にあります。

## D1 の上限

- 1 クエリの束縛変数は 100 個、SQL 文は 100 KB まで
- 1 回の呼び出しのクエリ数は Free で 50、Paid で 1,000 まで
- イベント数百件を 1 行ずつ入れると、Free では上限に当たるおそれがある
  - 配列を JSON で 1 つの変数に渡し、`json_each` で展開して入れる形にする

## D1 の書き込みの行数

同期は編集のたびに走るので、1 回の PUT が書く行数を小さくします。2026-10-14 に見直しました。

| プラン | 書き込み | 読み取り |
| --- | --- | --- |
| Workers Free | 1 日 10 万行まで。超えると、その日のクエリが失敗する | 1 日 500 万行まで |
| Workers Paid | 月 5,000 万行まで込み。超えた分は 100 万行あたり 1 ドル | 月 250 億行まで込み |

- 索引のある列を書くと、索引の分も 1 行と数えられる
- 見直す前は、PUT のたびに経由地とイベントをすべて消して入れ直していた。イベント 300 件・経由地 40 個の走行で、1 回に約 2,000 行を書く計算になる。Free では、1 日に 50 回ほどの同期で上限に届く
- いまは、変わった行だけを書く。同じ走行で、手元の D1 が返した行数は次のとおり

| 操作 | 書いた行数 |
| --- | --- |
| 初めて置く | 982 |
| 何も変えずに置く | 1 |
| イベント 1 件の時刻を確定する | 3 |
| 手前のイベントを 1 件消す | 580 |

- イベントを足したり消したりすると、後ろのイベントの並びの番号（`seq`）がずれて、その分を書く。経路を直したときも、後ろのイベントの位置が変わるので同じである
- 推定した時刻は送らない。送ると、確定のたびに、まわりのイベントの行がみな変わる
- 「約 2,000 行」は、初めて置くときの行数を 2 倍した見積もりで、測ってはいない
