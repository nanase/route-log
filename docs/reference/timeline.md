# 時間軸

すべての時刻は動画のタイムコードではなく実時刻（JST、ミリ秒精度）で持ちます。動画は複数ファイルに分かれ、編集後に削除されるため、実時刻を基準にすればログとして残り、将来の GPS ログとも重ねられます。

## 動画ファイルの扱い

- ドラレコは 16GB を上限に動画を分割し、ファイル名に録画開始時刻を記録する
- 各ファイルについて `開始時刻 = ファイル名から解析`、`長さ = ffprobe` で実時刻の範囲 `[start, start + duration)` を求める
- ファイルを開始時刻順に並べ、隙間（録画停止）や重なりも表現できる「仮想タイムライン」として扱う
- DJI Action 4 のファイル名は DJI_20261003050500_0004_D.mp4 の形式（録画開始の年月日時分秒〈JST〉と 4 桁の通し番号）。分割された各ファイルのファイル名時刻は、そのファイル自身の録画開始時刻であることを確認済み。開始時刻はこれを解析し、並び順は通し番号でも確認する。機種変更に備え、解析は正規表現の設定で差し替えられるようにする
- 拡張子は大文字の `.MP4` で記録される。解析は大文字・小文字を区別しない
- 1 つのフォルダに複数日のファイルが混ざることがある。下のフォルダまで読み、走行の日付と録画開始の日付（JST）が同じ動画だけを使う
  - ほかの日付の動画は、ファイル名の時刻で除き、ffprobe にかけない
- 分割の継ぎ目では、ファイル名の時刻に最大 2 秒ほどの重なり・隙間が出る
  - 実測は 3 か所で −1.0 秒、+0.4 秒、−2.1 秒
  - 5 秒以内の隙間は連続録画として扱い、録画停止にしない
  - 重なるときは、後のファイルが始まった所で前のファイルを切る
- 同じ日のフォルダに、走行と関わりの無い動画が混ざることがある。走行（日付）ごとに、タイムラインから外す動画を選べる
  - 外した動画は、再生、タイムライン、時刻と動画の位置の変換、CSV の動画の位置のどれにも使わない
  - 外した動画の時間は、録画停止と同じ扱いになる。推定時刻がそこに入ったイベントには、警告が付く
  - 動画はファイル名で見分ける。動画のファイルには触らない

## 実ファイルの中身

6 本で確かめました。

| 項目 | 値 |
| --- | --- |
| 映像 | HEVC Main 10（10 bit）、1920x1080、29.97 fps、25〜30 Mbps |
| 音声・その他 | AAC モノラル、DJI のメタデータ 2 本、タイムコード、サムネイル |
| 全体のビットレート | 約 32 Mbps。17 GB で 71〜85 分 |

2026-10-03 の走行の動画は、上と違っていました。撮るときの設定で変わるので、フレームレートと音のチャンネルは決め打ちしません。

- 映像は 59.94 fps（60000/1001）、約 34 Mbps だった
- 音は、16 本のうち 13 本が 1 チャンネル（モノラル）の AAC で、0008〜0010 の 3 本だけが 2 チャンネルで両方に同じ音が入っていた（ffprobe の `channels`）
  - Resolve では、モノラルのファイルも 2 チャンネルで、2 チャンネル目が無音のように見える

## ffprobe の探し方

- 環境変数 `ROUTELOG_FFPROBE`、`config.json` の `ffmpeg_dir`、PATH の順に探す
- PATH では、mise は `.cmd` の形で置くので、`.exe`・`.cmd`・`.bat` の順に探す
- 開発中は `mise exec --` 経由でアプリを起動する。そうしないと PATH に ffprobe が無い
- `ffmpeg_dir` は、起動したときに PATH で最初に ffprobe が見つかるフォルダに ffmpeg もあれば、そのフォルダを覚える。開発中の起動で覚え、リリースビルドを直に起動したときに使う
  - mise exec を通すと、PATH の先頭近くに mise の `.mise-bins` が入る。中の `.cmd` は ffmpeg の環境（PATH など）を整えてから exe を呼ぶ。覚えるのはこのフォルダで、リリースビルドも同じ `.cmd` を呼ぶ
  - mise の shim（`mise/shims`）は覚えない。起動した場所の `mise.toml` で版を決めるので、リポジトリの外では動かない
  - PATH で最初に見つかるのが shim なら、`mise which ffprobe` で `.mise-bins` を尋ねて覚える。mise exec を通さずに `bun tauri dev` で起動すると、こうなる。リポジトリの外では、mise は答えない
  - 当初は shim を見つけたら何もしなかった。そのため、mise exec を通さない起動では覚えられず、`ffmpeg_dir` が空のままだった
  - PATH にある別の ffmpeg（古い版で、ffprobe が無い）より、覚えた場所を先に使う
- 1 本あたり約 0.25 秒かかる。並列に呼び、14 本で 3.6 秒だった

## 時刻の変換

- 実時刻 → 動画位置：その時刻を含むファイルと、ファイル内のオフセット秒を返す
- 動画位置 → 実時刻：`ファイルの開始時刻 + 再生位置`
- どのファイルにも含まれない時刻（録画停止中）は、変換不可として扱う

## 時計の補正

- ドラレコの内蔵時計はずれることがあるため、走行ごとに補正値 `clock_offset_ms` を 1 つ持つ
- 表示・書き出しには `ファイル名の時刻 + clock_offset_ms` を使う
- 補正値は、時刻表示のある看板などを見て手で設定する
- 補正値を後から変えると、動画を見て確定した時刻は一緒に動く。手で入れた時刻は動かない
  - 動画で確定したイベントは、カメラの時計での時刻（`camera_ms`）も持つ。通過時刻はそれに補正値を足して求め直す

## 求める精度

時刻は 1 分以内のずれなら無視でき、数分でも問題になりません。秒単位の誤差を潰す仕組みは入れず、上の補正値を手で指定できれば足ります。

## Resolve との対応

Resolve 上では元ファイルのソースタイムコードで位置を指定するため、書き出し時に「ファイル名＋ファイル内オフセット」に変換します（[Resolve へ書き出す](resolve.md#resolve-へ書き出す)）。

クリップに埋め込まれたタイムコードは 0 始まりではなく時刻で、ファイル名の時刻より 20〜29 秒進んでいます。ファイル内オフセットで位置を示すので、この差は書き出しに影響しません。

- タイムコードは 29.97 fps のドロップフレームで付いている。映像は 59.94 fps である
- 差はファイルごとに違い、同じ日の中でも縮んでいく。2026-10-03 の走行では、朝の +26 秒から夕方の +19 秒まで縮んだ
- タイムラインのファイル（FCPXML）では、クリップの位置をソースのタイムコードで書く。そのため、ファイルごとにタイムコードを ffprobe で読み、ファイル内オフセットに足す（[Resolve へ書き出す](resolve.md#resolve-へ書き出す)）
