# Resolve 連携

DaVinci Resolve での編集に、ルートログの結果を渡す仕組みです。連携の範囲、いまの編集の流れ、停車の検出、書き出すファイルの形を扱います。

## Resolve 連携の範囲

2026-10-24 に範囲を決めました。

いちばん手間のかかる信号待ちのカットと、字幕の位置決めを減らします。Resolve は無料版を使うので、Resolve を外から操作せず、読み込めるファイルを書き出します。

やることは次の 4 つです。1 を先に作り、そのあと 2・3 と 4 を並行して作りました。

1. パート：YouTube に上げる 1 本ぶんの範囲
   - 走行の中に、始まりと終わりの経由地で決める。走行ごとにいくつでも作れる
   - 前後のパートで範囲が重なってもよい。まれに、前のパートの終わりを次のパートの頭にも使う
   - 5 時間を超えたら知らせる。止めはしない
   - 作った。画面と持ち方は [パート](ui.md#パート) にある
2. 停車の検出
   - 作った。測り方は [停車の検出の作り](#停車の検出の作り) に、画面は [いまの画面](ui.md#いまの画面) に、持ち方は [ローカルの保存](architecture.md#ローカルの保存) にある
   - 音と映像の動きで、信号待ちを含む停車の候補を出す（[停車を音と映像の動きで見分ける](#停車を音と映像の動きで見分ける)）
   - 走行ごとにボタンで始め、裏で動かす
   - 候補はアプリのタイムラインに帯で出し、採る・外すを選ぶ。既定は「採る」
   - 結果は、外した動画の覚えと同じく手元だけに持つ
3. 書き出し：パートごとに、ソースのタイムライン（FCPXML）とマーカーの EDL を 1 組
   - 作った。形は [Resolve へ書き出す](#resolve-へ書き出す) にある
   - FCPXML では、アプリで入れた停車と採った候補を抜く。音は両方のチャンネルに 1 チャンネル目を割り当てる。59.94 fps のドロップフレーム、3840×2160 にする
   - マーカーは、字幕を出すイベントを種類ごとの色で付ける
   - パートのタイムラインはそのパートのソースを頭から丸ごと包むので、同じ EDL をパートのタイムラインに読み込めば字幕の位置になる
4. 概略図の動画をパートに対応させる
   - まず全部のパートを合わせた経路を見せ、次にこのパートの経路へ寄る
   - このパートの経路だけをはっきり描き、他のパートの経路は半透明で薄く描く
   - 全経路を見せる時間、寄る時間、止めて見せる時間を調整できる。全体が 10 秒に収まらなくてよい
   - 作った。見せ方は [概略図の動画](output.md#概略図の動画) にある

やらないことは次のとおりです。

- Resolve を外から操作すること。スクリプトも MCP も、21.1 から Studio だけの機能である
- 字幕の文字や標識のクリップそのものを Resolve に置くこと。マーカーで場所を示すまで
- 候補の始まりと終わりを、アプリで細かく直すこと
- 色の調整、BGM、マスターのタイムライン

受け入れ条件は次のとおりです。

- 10-03 の走行を 2 つのパートに分けて書き出す
  - 無料版の 21.1.1 で読むと、試作と同じく、タイムコード・マーカー・抜いた停車・2 チャンネルが合う
  - パートのタイムラインにマーカーの EDL を読み込むと、字幕の位置に来る
- 0005 の最初の 20 分で、目で確かめた 10 件と同じ候補が出る
- 前半のパートの概略図の動画で、全経路を見せてから前半へ寄り、後半の経路が薄く残る

2026-10-24 に 4 つとも main に入り、受け入れ条件を確かめました。

- 書き出しは、利用者がリリースビルド（0b87e91）で 10-03 のパートを書き出し、無料版の 21.1.1 で読み込んで確かめた
- 停車の候補は、0005 の 10 件と位置も長さも一致した
- 概略図の動画は、往路のパートの見本を利用者が見て確かめた
- 本番の D1 にマイグレーション 0003 を当て、Worker をデプロイした。利用者が、パートを作った走行をアプリから本番へ同期できることを確かめた

ここからは、範囲を決めるまでに調べて確かめたことです。

- 当初は、Resolve 側の Python スクリプトでクリップにマーカーを付ける案だった（`MediaPoolItem.AddMarker`）
- Resolve 21.1（2026-09）から、スクリプトは Studio でしか動かない。無料版では、この案は使えない
  - Python 2 は、どちらの版でも使えなくなった
- 21.1 の Studio には MCP サーバが入り、Claude Code などから会話で Resolve を操作できる
  - 中身はスクリプトの API を呼ぶもので、できることは API の範囲に留まる
- 無料版でも使えるのは、タイムラインのファイル（FCPXML、OTIO、EDL）を書き出し、Resolve で読み込む方法である
  - 読み込みはスクリプトではなく画面の操作なので、21.1 の制限に掛からない
  - 2026-10-24、使い捨ての試作で、無料版の 21.1.1 が FCPXML 1.10 とマーカーの EDL を読むことを確かめた。分かったことは、[Resolve へ書き出す](#resolve-へ書き出す) に本番の形で書いた
- 音はモノラルで録っている。編集では疑似ステレオにする前に、2 チャンネル目にも 1 チャンネル目を割り当てる。この割り当ては FCPXML で渡せる

## Resolve での編集の流れ

2026-10-24 に利用者から聞き取りました。

いまの編集は、タイムラインを 3 段に重ねて作っています。

1. 元の動画を、加工せずにメディアプールへ読み込む
2. 「ソース」のタイムラインに、読み込んだ動画をそのまま並べる
   - この時点では元の動画のタイムコードが生きていて、時刻が分かる
   - 1 本が 5 時間を超えないようにする。超えるなら、別のソースのタイムラインに分ける
   - 編集の都合で、別のタイムラインと同じ場面が重なることがある
3. ソースのタイムラインで、停車している場面を切る
   - 長い停車のほかに、信号待ちも切る。信号待ちは数秒から数分までまちまちで、数が多い
   - アプリに入れている停車は長い停車だけで、信号待ちは入れていない
   - 停車かどうかは人が見て決める。Resolve で排気音が小さくなった所を探し、映像を見て正確な時刻を決める
   - 映像の動きだけでは決めない。トンネルのような暗い所では、走っていても動きが小さく見えるためである
   - 編集でいちばん時間がかかるのが、この作業である
4. ソースのタイムラインを包む「パート」のタイムラインを作り、字幕と標識の画像を載せる
   - 字幕は Text+ などのタイトルで載せる
   - 標識は、値を指定して出し分ける自作のクリップで、画像と同じように置ける
   - ルートログのデータを使うのはここである
   - パートの上では、元の動画のタイムコードが分からなくなっている
5. パートの上で、ソースの明るさと彩度を整え、音を疑似ステレオにするなどの効果を掛ける
6. パートを包む「マスター」のタイムラインを作り、概略図の動画、BGM、パート、アウトロを並べて仕上げる

Resolve のプロジェクトは、2026-10-24 から次の設定で作っています。

- タイムラインのフレームレートは 59.94 で、ドロップフレームのタイムコードを使う
  - これまでは 60 だった。素材は 59.94 なので、60 では約 16.7 秒ごとに 1 フレームが繰り返される
  - フレームレートは、素材を入れたあとでは変えられない
- タイムラインの解像度は 3840×2160 のままにする
  - YouTube で十分なビットレートを得るため、4K で書き出す。素材はフル HD である
  - 編集が重いのは、無料版が H.265 の 10 bit を CPU でデコードするためで、解像度のためではない。タイムラインプロキシやプロキシで軽くする
- データレベルは既定のまま（ビデオ）にする。これまではプロジェクト設定で「フル」にしていた。素材は限定レンジ（BT.709）である

## 停車を音と映像の動きで見分ける

信号待ちを切る手間を減らせるかを、2026-10-03 の動画 3 本で測りました。音と映像の動きを組み合わせれば、信号待ちも長い停車も見分けられる見込みです。

- このカメラの録音では、止まると音が大きくなる。停車中は -14 dB 前後でほとんど揺れず、走ると -17 dB 前後に下がる
  - 信号待ちも 10 分の停車も、ほぼ同じ値だった。理由は確かめていない
- 映像の動きは、1/12 に縮めたグレースケールの隣のフレームとの差で測る。止まると、動いた画素がほぼ 0% になる
- 動きだけでは、トンネルの中も停車に見える。トンネルの中の音は走行と同じなので、音で除ける
- 音だけでは、ゆっくり走る所も拾う。市街の 20 分で、音の候補 21 件のうち、止まっていたのは 10 件だった
- 試した規則：動いた画素が 1% 未満で、音が -15.3 dB 以上の秒が、3 秒以上続く
  - 市街の 20 分では、動きで拾った 10 件がすべて残り、トンネルは 0 件になった
  - 録画中の既知の停車（10 分半）とは、端で数秒の差で一致した
- 利用者が Resolve で候補 10 件を目で確かめた（0005 の最初の 20 分）。精度は十分だった
  - 走り出しは、ほぼ正確だった
  - 止まり始めは、実際より 1〜2 秒遅れた。許容の範囲である
- 時間：音は 1 時間ぶんで 2〜3 分。動きは GPU でデコードして 1 時間ぶんで 9〜11 分。音の候補の前後だけ動きを測れば、短くできる
- 残る心配
  - -15.3 dB は、この日の値から決めた。前後との差を使うほうが、他の日にも効きやすい
  - 雨、大きな車の隣、渋滞のようにゆっくり進む所は見ていない

## 停車の検出の作り

2026-10-24 に実装しました。

上の測定の規則を、測る時間を縮めてアプリに入れました。解析は `routelog-video` の `stops`（規則）と `StopMeter`（ffmpeg の呼び出し）にあります。

- 2 段で測る
  1. 動画の全体を 1 度読み、1 チャンネル目の音の大きさ（1 秒ごとの RMS）と、キーフレームの差を測る。キーフレームは 0.5 秒おきにあり、それだけをデコードする（`-skip_frame nokey`）
  2. 音が -15.3 dB 以上で、キーフレームの差で動いた画素が 5% 未満の秒が 2 秒以上続く所の、前後 8 秒を足した窓だけ、全部のフレームを読み、試作と同じく 0.1 秒ごとの差を測る
  - 候補は、試作と同じ規則で 2 段目の値から出す。動いた画素が 1% 未満で、音が -15.3 dB 以上の秒が 3 秒以上続く。切れ目が 2 秒以下ならつなぐ
- キーフレームだけで判定しない。キーフレームは 0.5 秒離れているので、止まりかけの遅い動きも大きく出る。0005 の最初の 20 分では、止まり始めが試作より 2〜5 秒遅れ、信号待ち 2 件が割れた
- 音は 1 チャンネル目だけを測る（`pan=mono|c0=c0`）。2 チャンネルのファイル（0008）も、停車 -14.0 dB、走行 -17.4 dB で、モノラルのファイルと同じ閾値で判定できた
  - 試作で見込んでいた「混ぜると約 6 dB 大きく出る」ことは、ffmpeg の混ぜ方では起きないはずだが、確かめていない。1 チャンネル目だけなら、混ぜ方に依らない
- 長い停車をつなぐ。2 つの候補の切れ目が 60 秒以下で、その間に音が -15.3 dB を下回る秒が 7 秒以上続かなければ、同じ停車とみなしてつなぐ
  - 0013 の録画中の停車（10 分半）は、停車中も画面の半分が動く場面があり、動きの規則だけでは 16 件に割れた。つなぐと、00:19:59 から 625 秒の 1 件になった
  - 6 秒は、0013 の切れ目の中でいちばん長く音が下がった所（6 秒）から決めた。0005 で走ってから次に止まった所は、8 秒以上下がっていた。1 例から決めた値である
- GPU が使えなければ、ffmpeg が CPU でデコードする（`-hwaccel auto`）。作業機では DXVA2 が選ばれた
- 時間：作業機（GTX 1080）で、1 時間の動画に 3〜5 分（1 段目が約 1.5 分）。細かく測った窓は、5 本で動画の 2〜28% だった
  - CPU では、キーフレームだけで 1 時間に約 4.5 分、全部のフレームで 1 秒ぶんに約 0.3 秒かかる。1 時間の動画に 8 分ほどの見込み
- 測った値は、ffmpeg のログから読む。フィルタに名前を付け（`metadata@motion`、`ametadata@sound`）、その名前の行だけを拾う
- 2026-10-03 の走行で確かめた結果
  - 0005 の最初の 20 分で、試作の 10 件と位置も長さも同じ候補が出た
  - トンネル（0005 の 00:38:13 付近、0004 の 00:36:27 付近と 00:39:10 付近）は、候補にならなかった
  - 0013 の録画中の停車は、1 件になった
  - 2 チャンネルの 0008 でも、モノラルのファイルと同じ閾値のまま、00:16:58 から 106 秒の停車などの候補が出た
  - 1 本ずつ確かめるには、`cargo run -p routelog-video --example find_stops -- <動画>` を使う

## Resolve へ書き出す

2026-10-24 に実装しました。

パートごとに、停車を抜いたソースのタイムライン（FCPXML 1.10）と、字幕を出す所のマーカー（EDL）を 1 組書きます。タイムラインとファイルの中身は `routelog-core` の `resolve` で作り、素材の中身は `routelog-video` の `Ffprobe::media` で読みます。

- 経路入力のパートの欄で、書き出しのボタンを押す。押すたびに書き出し先のフォルダを選ぶ。前に選んだフォルダから開く
  - 名前は「走行の題 パートの名前 ソース.fcpxml」と「走行の題 パートの名前 マーカー.edl」。パートの名前が空なら「パート n」と呼ぶ。ファイル名に使えない字（`\ / : * ? " < > |`）は `_` にする
  - 書き出し先と名前の付け方は、2026-10-24 に利用者と決めた
  - 同じ名前のファイルがあれば書かずに知らせ、「上書きする」で書き直す
  - 書き終えたら、タイムラインの長さ、抜いた停車の数と長さ、マーカーの数と、マーカーの読み込み方を緑の帯に出す。閉じるまで残る
  - パートの範囲が正しくない、動画が無い、端の時刻が推定できていない、範囲に録画が無いときは、ボタンを押せない。理由はボタンの説明に出す
- 範囲：パートの両端の経由地を通った推定時刻の間で、録画している所だけを並べる。走行から外した動画は使わない
  - 終わりの経由地を通った時刻で切るので、そこにある到着のイベントはタイムラインの外になり、マーカーにならない
- 抜く所：停車のイベント（`stop`）と、停車の検出で採った候補。録画している所だけが効く
  - 候補は動画の中の位置で持っているので、実時刻にする。後の動画が始まった所で前の動画を切る扱いは、タイムラインの帯と同じ
- 時間は、すべて 59.94 fps のフレーム（1001/60000 秒）の数で持つ。実時刻のミリ秒は、いちばん近いフレームに丸める
- 素材は、範囲にある動画だけを ffprobe で並べて読む。読むのは、フレームレート、フレームの数、大きさ、音のチャンネルの数、タイムコードである
  - 59.94 fps でない動画が範囲にあれば、書き出さない。どのファイルが何 fps かを知らせる。Resolve のプロジェクトが 59.94 fps だからである（2026-10-24 に利用者と決めた）
  - タイムコードは、59.94 fps の映像にも、カメラが 29.97 fps のドロップフレームで付けている。その 2 倍を 59.94 のフレームの数にして、素材の頭（`asset` の `start`）にする
  - タイムコードとファイル名の時刻のずれはファイルごとに違うので、必ず読む。読めなければ書き出さない
- FCPXML
  - タイムラインは 3840×2160、59.94 fps、ドロップフレーム。素材には自分の大きさ（1920×1080）の `format` を持たせ、Resolve に引き伸ばさせる
  - タイムラインは 01:00:00;00 から始める（`tcStart`）。クリップの位置（`offset`）も、そこから数える
    - パートのタイムラインを、Resolve の既定の 01:00:00;00 始まりで作っているので、合わせた（2026-10-24 に利用者と決めた）。試作は 0 始まりだった
  - 素材は、元の MP4 を file URL で指す。空白と日本語は、UTF-8 のバイトごとにパーセントで書く
  - 音は、クリップの中に `audio-channel-source` を 2 つ書き、1 チャンネル目を L と R にそれぞれ割り当てる。2 チャンネルの素材にも同じに書く
    - 1 つの `audio-channel-source` に `srcCh="1, 1" outCh="L, R"` と書くと、Resolve はモノラルとして読み、左からしか音が出なかった
  - マーカーは書かない。`asset-clip` の中の `marker` は、Resolve が 1 つも読まなかった
- マーカーの EDL
  - Resolve の「EDL からタイムラインマーカー」で読む形。`FCM: DROP FRAME` で、位置は 59.94 のドロップフレームのタイムコードで 01:00:00;00 から数える。1 件ごとに `|C:色 |M:名前 |D:1` を付ける
  - 入れるのは、字幕にするイベント（`hidden` でない）のうち、経路の上でパートの範囲にあるもの
  - 録画の外、抜いた所、時刻が推定できていないイベントは入れず、その数を知らせる。停車のイベントは、抜いた所の頭にあるので入らない
  - 名前の無いイベントは、種類の呼び名（「橋」など）で呼ぶ。名前の `|` は `/` に、改行は空白にする
  - 色は種類で分ける。出発・到着は赤、路線は青、県境と市区町村境は緑、橋は水色、トンネルは紫、道の駅は黄、ほかはクリーム
  - マーカーは、通った時刻より前へずらして置く（2026-10-25 に利用者と決めた）。利用者は、字幕を 1 秒ほどかけてフェードインさせるため、通る 2 秒ほど前に入れている。ドラレコの動画なので、早めに出すほうが読みやすくもある
    - ずらす長さは、色と同じ 7 つの分け方ごとに決める。既定はどれも 2 秒
    - 設定のダイアログの「マーカーの前倒し」で、0.5 秒刻みに変えられる。`config.json` の `marker_leads` に持ち、この PC だけで使う。クラウドには送らない
    - ずらすのは、停車を抜いたあとのタイムラインの上で行う。頭より前にはしない
    - 種類で長さが違うので、通った順とマーカーの順が入れ替わることがある
- Resolve での読み込み
  - FCPXML は、ファイル > 読み込み > タイムライン で読む
  - マーカーは、メディアプールでタイムラインを右クリックし、「タイムライン」>「読み込み」>「EDL からタイムラインマーカー」で読む
    - ファイル > 読み込み > タイムライン で読むと、マーカーを素材のクリップとみなし、オフラインのクリップが並ぶ
